# Methodology — H100 reproduction (node: dapperdingo-002)

How each number in `summary.md` was produced, and the pitfalls that affect correctness.
Everything here is regenerated by `run_suite.sh`; raw stdout lives in `raw/`.

## Platform

- GPU: NVIDIA **H100 80GB HBM3 (SXM5)**, sm_90, 132 SMs, boost 1980 MHz, 50 MB L2, HBM3.
- Toolkit: **CUDA 12.9** (`nvcc` on PATH), driver 575.x. Ubuntu.
- Exact snapshot: see `env/deviceQuery.txt`, `env/nvidia-smi.txt`, `env/gpu-spec.csv`, `env/nvcc.txt`.
- Compared against the paper's **H800 PCIe** column (arXiv:2501.12084, Tables II–XI).

## What each benchmark measures

| Metric | Binary | Method | Units |
|---|---|---|---|
| FP32/16/64/INT throughput | `MaxFlops*` | fully-unrolled FMA loop, one warp/SM | flop/clk/SM |
| Instruction latency | `alu_lat_*` | dependent op chain | clk |
| L1 latency | `l1_lat` | pointer chase, 32 KB array (fits L1) | cycles |
| L2 latency | `l2_lat` | pointer chase, array > L1, < L2 | cycles |
| Shared latency | `shared_lat` | pointer chase in shared mem, /ITERS | cycles |
| Global latency | `mem_lat` **(patched)** | pointer chase, array **> L2** | cycles |
| L1/L2/shared BW | `l1_bw_*`,`l2_bw_*`,`shared_bw*` | vectorized load loop | byte/clk(/SM) |
| HBM BW | `mem_bw` | streaming copy | GB/s |
| MMA (warp) | `TensorCores/mma/*` | `mma.sync`, single_SM + all_SM | TFLOPS/TOPS |
| WGMMA (warpgroup) | `TensorCores/wgmma/throughput` | 100k dependent `wgmma`, 1 warpgroup/SM | TFLOPS/TOPS |

## Pitfalls (correctness-critical)

### 1. `mem_lat` measures L2, not DRAM, out of the box
Default `#define ARRAY_SIZE (8*1024*128)` = **8 MB**, which fits entirely in the H100's
**50 MB L2**. So the stock binary reports ~300 cycles — that is an **L2-resident** latency,
not global memory. `run_suite.sh` rebuilds it with `ARRAY_SIZE = 62914560` (≈480 MB, > L2) as
`mem_lat_dram`, which reports ~1047 cycles. Use the `_dram` value for "global memory latency".
On B200 (larger L2) this array must be scaled up again.

### 2. Exclusive GPU access is mandatory (a benchmark can look ~2× slow under contention)
While first exploring WGMMA we measured fp16 at only ~484 TFLOPS (half of spec) and briefly
concluded it was an under-saturation/codegen anomaly. **It was not** — a separate `mma`/`mmasp`
batch was still running on the *same* GPU at the time, so the two workloads shared the SMs and
each ran at ~half rate. With exclusive access, `wgmma` fp16 measures **~976 TFLOPS** (vs H100's
~989 dense-fp16 spec), fp8/int8 **~1951**, tf32 **~488** — all on-spec. Lessons baked into
`run_suite.sh`:
- Run benchmarks **one at a time on a dedicated GPU** (`CUDA_VISIBLE_DEVICES`); never launch a
  second GPU job (even your own analysis script) during a measurement.
- Take the **peak across the ss/rs × zero/random configs** the binary emits, not a single line.
- When a tensor-core number looks low, first check for co-tenants (`nvidia-smi`) and confirm
  clock+power *during* the kernel (short kernels can finish before a naive sampler starts).

### 3. Cross-GPU latency comparison needs clock normalization
Latencies are reported in SM clock cycles. H100 boosts to 1980 MHz vs H800's 1755 MHz, so the
same nanosecond latency shows ~13% more cycles on H100. Keep this in mind when a cycle count is
"higher" than the paper's.

### 4. Clock is recorded, not locked
The H100 holds 1980 MHz under all these loads (verified), so `run_suite.sh` does not force clocks
(which would disturb a shared node). `env/` + per-run behavior document the clock; if you port to a
part that throttles, add `sudo nvidia-smi -lgc <clk>` and reset afterward.
